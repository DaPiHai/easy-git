## 1. 产品概述

### 1.1 背景与问题

Git 是事实上的版本控制标准，但命令行学习曲线陡峭：约 170 个命令、大量隐式概念（暂存区、HEAD、reflog、分离头指针），新手容易因误操作（`reset --hard`、`force push`）丢失工作。现有 GUI 工具（GitHub Desktop、SourceTree、Fork 等）要么功能不全，要么对中文用户不友好，要么体积/内存臃肿。

### 1.2 产品定位

**一款轻量、跨平台的中文优先 Git 可视化桌面应用，让完全不会命令行的用户能安全地完成 Git 的全部常用与进阶操作。**

一句话卖点：*「不用记一条命令，也能放心用 Git。」*

### 1.3 已确认的关键决策

| 决策项 | 结论 |
| --- | --- |
| 平台形态 | 跨平台桌面应用（Windows / macOS / Linux），直接操作本地仓库，离线可用 |
| 目标用户 | 新手 + 专家双模式：默认简洁模式强引导防误操作，专家模式暴露全部高级操作 |
| 技术栈 | Tauri 2 + Rust 核心 + React 18 前端（框架决策 2026-09-08，详见 TDD §1） |
| 界面语言 | 中文优先，Git 术语做本土化翻译并保留英文命令标注；架构预留 i18n |
| 操作覆盖 | 核心 + 进阶全覆盖（约 65–75 个命令），不含底层 plumbing 命令的界面暴露 |
| 可视化亮点 | 提交历史 DAG 图、三区状态可视化、Diff 对比 + 逐块暂存、冲突解决向导（四项全部重点打磨） |
| 平台集成 | GitHub / GitLab / Gitee 多平台深度集成（PR/MR、Issue、通知） |
| 仓库管理 | 多仓库管理 + submodule / worktree 可视化管理 |
| 安全策略 | 全操作可撤销：破坏性操作前自动快照点，reflog 可视化支持一键撤销任意历史操作 |
| 性能目标 | 支持 10 万+ 提交的超大型仓库流畅浏览 |
| 开源策略 | 开源（MIT 或 Apache-2.0，社区共建） |
| 版本路线 | 三阶段演进：MVP 本地全流程 → 远程协作 + 平台集成 → 进阶工具与打磨 |

### 1.4 产品目标（可衡量）

1. 零命令行可用性：新手用户在无任何文档辅助下，10 分钟内独立完成「克隆 → 修改 → 暂存 → 提交 → 建分支 → 合并」全流程。
2. 覆盖率：覆盖日常 Git 工作流 95% 以上的操作场景（对应附录 A 命令映射表）。
3. 安全性：任何 GUI 操作造成的仓库状态改变均可通过应用内「撤销」恢复到操作前状态。
4. 轻量：安装包 ≤ 30 MB，冷启动 ≤ 2 s，空闲内存 ≤ 300 MB（对比 Electron 系工具显著降低）。
5. 大仓库：10 万+ 提交仓库的历史浏览滚动帧率 ≥ 50 fps，状态刷新无卡顿。

### 1.5 非目标（明确不做）

- 不内置可输入任意命令的终端（提供只读的「命令透视」用于学习，见 §5.12）。
- 不做代码编辑器 / IDE，不做代码文本编辑能力（仅查看与 diff）。
- 不支持 SVN / Perforce / CVS 等其他版本控制系统互操作。
- 不做自建仓库托管服务；平台集成使用各平台官方账号与 API。
- 不在界面上暴露底层 plumbing 命令（`cat-file`、`rev-parse` 等），它们仅作为内部实现。

## 2. 目标用户与使用场景

### 2.1 用户画像

| 画像 | 描述 | 核心诉求 | 使用模式 |
| --- | --- | --- | --- |
| 小林（新手） | 大三学生/初入职场的开发者或非开发角色（设计、产品），从未用过命令行 Git | 不知道自己该做什么；怕把仓库搞坏；看不懂报错 | 简洁模式：向导式流程、术语翻译、防误操作 |
| 老王（熟手） | 3–10 年开发者，熟练命令行，希望 GUI 提效 | 快捷键、批量操作、高信息密度、精确控制 | 专家模式：完整参数面板、原始 diff/日志视图 |
| 周姐（多仓库维护者） | 维护 10+ 个项目仓库的技术负责人/开源维护者 | 仓库总览、批量同步、跨仓库搜索、子模块管理 | 多仓库工作台 |
| 团队协作者 | 通过 GitHub/GitLab/Gitee 协作的任意上述用户 | 不离开应用完成 PR/MR 流程 | 平台集成面板 |

### 2.2 核心用户故事（节选，验收时逐条走查）

- 作为新手，我打开应用后能看到「克隆仓库 / 新建仓库 / 打开本地仓库」三个大按钮和引导说明。
- 作为新手，我修改文件后，应用在首页直接提示「你有 3 个文件变更」，我勾选文件、写一句说明、点「提交」即完成，全程不接触「索引」概念。
- 作为新手，我误删了一个分支，能在「回收站」里一键找回。
- 作为新手，我遇到冲突时，向导逐个冲突引导我选择「保留我的 / 保留对方的 / 手动合并」，而不是让我看 `<<<<<<<` 标记发呆。
- 作为熟手，我按 `Ctrl+Shift+A` 唤起命令面板，输入文件名直接 stage；我在提交框里用 `Ctrl+Enter` 完成提交。
- 作为熟手，我在 DAG 图上选中两个提交做 range-diff，对分支做交互式 rebase（拖拽调整提交顺序、squash、edit）。
- 作为维护者，我在仓库列表一眼看到每个仓库的未推送/未拉取数量，一键批量 fetch。
- 作为协作者，我在应用内完成 fork → 分支 → 提交 → push → 创建 PR → 查看评论 → 合并 PR 的完整闭环。

## 3. 设计原则

1. **零命令行（No-Terminal）**：所有功能必须可通过鼠标/键盘在界面中完成；每个操作提供等价 git 命令的「命令透视」（默认折叠），既是学习工具也是调试依据。
2. **全操作可撤销（Safety Net）**：破坏性操作（重置、强制推送、变基、删除分支、丢弃修改）执行前自动创建快照点；撤销能力基于 reflog 时间线可视化，覆盖任意历史操作。
3. **术语即教学**：界面用中文术语（见 §6.7 术语表），悬浮提示给出 git 原词与解释；出错信息必须「人话化」并给出下一步建议按钮。
4. **渐进披露（双模式）**：简洁模式隐藏高级概念与危险参数；专家模式全部呈现，且可随时切换，不丢失状态。
5. **轻量自律**：功能增加不得显著增加包体与内存；后台任务全部异步，UI 永不因仓库大小而冻结。

## 4. 技术架构

### 4.1 总体架构

```
┌────────────────────────────────────────────────────┐
│ 前端 UI 层（Web 技术 + 系统 WebView）                 │
│  简洁/专家双模式视图 · DAG 图渲染 · Diff 视图 · 向导    │
├────────────────────────────────────────────────────┤
│ Tauri 2 IPC（类型化命令 API + 事件推送）               │
├────────────────────────────────────────────────────┤
│ Rust 核心层                                          │
│  ├─ git-core：Git 交互层（git2-rs + git CLI 混合）    │
│  ├─ safety：快照点 / 回收站 / 撤销引擎                 │
│  ├─ providers：GitHub / GitLab / Gitee API 适配层     │
│  ├─ indexer：大仓库后台索引与缓存（commit-graph 等）    │
│  └─ fs-watch：文件系统监听与增量状态刷新               │
├────────────────────────────────────────────────────┤
│ 系统能力：git CLI（≥2.30）· 系统钥匙串 · 文件系统       │
└────────────────────────────────────────────────────┘
```

### 4.2 Git 交互层策略（关键技术决策）

| 操作类别 | 实现方式 | 示例 |
| --- | --- | --- |
| 读操作、常规写操作 | git2-rs（libgit2 绑定）：性能好、结构化数据适合 UI | status、log、diff、tree 遍历、commit、branch |
| 复杂/边界操作 | 调用 git CLI 子进程（解析 `--porcelain` 输出） | rebase 中断恢复、bisect、worktree、submodule、LFS、sparse-checkout |
| 凭据存储 | 系统钥匙串（Windows Credential Manager / macOS Keychain / Linux Secret Service） | HTTPS 密码、Token、SSH 密钥口令 |
| 仓库自动维护 | 后台静默执行 | gc、maintenance、pack-refs、prune（用户无感知） |

约束：git2-rs 未覆盖的能力（如部分 rebase 场景）必须以 CLI 兜底，UI 层无感知；所有 CLI 调用做超时与取消处理。

### 4.3 性能设计

- **历史/DAG 图**：虚拟滚动 + 分页懒加载（默认加载最近 500 条，滚动续读）；拓扑计算利用 `commit-graph` 文件，缺失时后台生成。
- **状态刷新**：fs-watch 增量监听 + 防抖，避免每次全量 `status`；大仓库用后台线程计算。
- **Diff 渲染**：逐块懒渲染；单文件 diff 超 5000 行时折叠并提示。
- **索引缓存**：仓库元数据（分支、贡献者、图形拓扑）本地缓存（LRU + 失效策略）。

### 4.4 安全引擎（safety）设计

- **快照点（Safety Point）**：执行危险操作前，自动记录分支引用备份（ORIG_HEAD + 自定义 `refs/easy-git/backup/*`），必要时将未提交修改自动 stash。
- **回收站**：删除的分支/标签/提交移动到 `refs/easy-git/trash/*`，默认保留 30 天，界面可恢复/彻底删除。
- **撤销引擎**：基于 reflog 时间线构建操作历史栈，UI 提供「撤销/重做」按钮，支持跳转到任意历史点回滚。
- **高危操作确认**：强制推送、`reset --hard`、历史重写类操作在简洁模式下弹出后果说明 + 二次确认；专家模式可配置降低打扰。

## 6. 可视化与交互设计

### 6.1 整体布局

```
┌──────────────────────────────────────────────────────────────┐
│ 顶栏：仓库切换 ｜ 当前分支 ▾ ｜ 获取 · 拉取 · 推送 · 同步 ｜ 搜索 │
├───────────┬──────────────────────────────────┬───────────────┤
│ 仓库栏     │ 主视图（页签切换）                  │ 详情面板        │
│ · 仓库列表 │ ① 变更（三区状态）                 │ · 提交详情      │
│ · 收藏分组 │ ② 历史（DAG 图）                  │ · 文件 diff    │
│ · 新建/克隆│ ③ 分支看板                        │ · 操作引导/向导  │
│           │ ④ 储藏 · 标签 · 子模块 · 工作树      │                │
├───────────┴──────────────────────────────────┴───────────────┤
│ 底栏：模式（简洁/专家） ｜ 撤销 · 重做 ｜ 命令透视 ｜ 任务/进度    │
└──────────────────────────────────────────────────────────────┘
```

- 主视图默认落在「变更」页：打开应用第一眼即知道「我要做什么」。
- 详情面板上下文驱动：选中提交/文件/冲突时切换内容。
- 底栏常驻「撤销/重做」与「命令透视」，强化安全与学习心智。

### 6.2 历史 DAG 图（重点亮点 ①）交互规格

- 渲染：SVG/Canvas 分道算法，分支按颜色区分（每分支一色，跨仓库一致）。
- 节点：普通提交圆形、合并提交菱形、当前 HEAD 高亮环、未推送/未拉取提交加角标。
- 操作入口：右键节点 → 提交详情 / 在此建分支 / 检出 / 变基到此处 / 摘取 / 回滚 / 重置到此处 / 复制哈希。
- 对比：按住 Shift 选两个节点 → 显示差异与 range-diff 入口。
- 过滤：分支选择器（全部/当前/多选）、作者、时间范围、搜索消息/哈希。
- 性能：默认 500 条虚拟滚动，滚动到底自动续载；拓扑缓存复用。

### 6.3 三区状态视图（重点亮点 ②）交互规格

- 顶部进度条隐喻：`工作区 → 暂存区 → 本地仓库 → 远程` 四站，徽标显示每站文件数/领先落后提交数。
- 变更列表分组：冲突（最优先，红色）、已暂存、未暂存、未跟踪。
- 每行：状态图标、文件路径、(+/-) 行数统计、快捷操作（暂存/撤销/预览）。
- 提交框固定在列表上方：只有暂存了文件才激活，空消息提交给出规范提示。

### 6.4 Diff 视图 + 逐块暂存（重点亮点 ③）交互规格

- 统一/并排双布局，行内高亮修改词级差异。
- 每个 hunk 悬浮操作条：暂存此块 / 撤销此块；展开后可选中行级子集操作。
- 大文件折叠策略与「只显示前 N 行」提示。
- 与三区视图联动：点击变更列表文件即在右侧打开 diff。

### 6.5 冲突解决向导（重点亮点 ④）流程

1. 检测到合并/变基冲突 → 全屏向导接管，顶部显示「正在解决合并冲突 3/7」。
2. 冲突文件列表（可跳过稍后处理）→ 进入单个文件三栏视图。
3. 逐冲突块决策（§5.8）→ 实时进度。
4. 全部完成 → 汇总页确认 → 标记解决 → 引导完成合并提交。
5. 任何一步可「中止」回到操作前。

### 6.6 双模式差异

## 8. 里程碑规划

### M1 — MVP：本地仓库全流程（目标周期建议 8–10 周）

**范围**：§5.1 仓库管理（P0）、§5.2 三区暂存、§5.3 提交/历史 DAG/diff/标签、§5.4 分支基础操作 + merge/revert/reset、§5.5 获取/拉取/推送/凭据、§5.7 储藏 + 操作时间线基础、§5.8 冲突向导（基础）、§5.10 设置基础、§5.11 自动维护、§5.12 命令透视与错误人话化。

**验收标准**：
1. 用户故事 §2.2 中新手前三条全部通过走查。
2. 10 分钟「克隆→改→提交→分支→合并」零命令行测试通过率 ≥ 90%（5 名无 Git 经验用户）。
3. 任意破坏性操作后均可一键撤销；删除分支可从回收站恢复。
4. 5000 提交仓库操作流畅；安装包与内存达标。

### M2 — 远程协作与平台集成

**范围**：变基（基础）、摘取提交、检出历史版本、远程分支管理、三平台账号绑定 + PR/MR 创建与浏览 + Issue 查看、快捷键与命令面板、冲突向导完善。

**验收标准**：完成 fork → clone → branch → commit → push → 创建 PR → 查看 CI/评论 → 合并 PR 全流程不出应用；强制推送有远端备份且可恢复。

### M3 — 进阶工具与打磨

**范围**：交互式 rebase、二分定位向导、子模块/工作树管理、blame 增强/notes/grep/shortlog/range-diff、补丁与归档导出、签名验证、通知聚合、Release 辅助、i18n 英文包、大仓库性能达标（10 万+ 提交）、自动更新。

**验收标准**：Linux 内核量级仓库（10 万+ 提交）浏览流畅；性能指标 §7 全部达标；覆盖命令数达到附录 A 目标（65–75 个）。
